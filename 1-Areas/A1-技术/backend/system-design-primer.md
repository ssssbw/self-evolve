```
你的 App 有 100 万用户时怎么办？

```

## 系统设计的核心概念

### 1. 分布式系统基础

| 概念 | 含义 | 类比你已有的知识 |
|------|------|-----------------|
| 负载均衡 | 把请求分发到多台服务器 | ListView.builder 按需加载（分摊压力） |
| 缓存 | 用快速存储暂存热点数据 | ImageCache（你已经理解了！） |
| 数据库分片 | 把数据拆分到多个数据库 | ListView 分页加载 |
| 微服务 | 把大系统拆成独立服务 | Flutter 的模块化架构 |
| 消息队列 | 异步处理任务 | Dart 的 Event Queue |
| CDN | 把静态资源放到离用户最近的节点 | 缓存层次结构（L1→L2→CDN） |

### 2. CAP 定理

分布式系统不可能同时满足三个：
- **C（一致性）**：所有节点看到相同数据
- **A（可用性）**：每个请求都能得到响应
- **P（分区容错）**：网络断开时系统还能工作

**现实：** 网络分区必然发生（P），所以只能在 C 和 A 之间选择。

### 3. 数据库选型

| 类型 | 适合 | 不适合 | 代表 |
|------|------|--------|------|
| 关系型（SQL） | 结构化数据、事务、复杂查询 | 海量非结构化数据 | PostgreSQL, MySQL |
| 文档型（NoSQL） | 灵活 schema、JSON 数据 | 复杂关联查询 | MongoDB |
| KV 存储 | 缓存、会话 | 复杂查询 | Redis |
| 时序数据库 | 监控数据、IoT | 事务 | InfluxDB |

## 常见系统设计题目

### 题目 1：设计一个短链接服务（bit.ly）

```
用户输入长 URL → 系统返回短 URL → 访问短 URL → 重定向到长 URL
```

**关键设计决策：**

1. **URL 映射存储**
   - KV 存储（Redis）最合适：short_url → long_url
   - 生成策略：自增 ID → Base62 编码（a-zA-Z0-9，6 位 = 568 亿种组合）

2. **重定向流程**
   ```
   用户访问 short.url/abc123
     → 查 Redis 缓存
       → 命中 → 302 重定向
       → 未命中 → 查数据库 → 写入缓存 → 302 重定向
   ```

3. **流量预估**
   - 100 万用户，每用户每天 10 次访问 = 1000 万 QPS
   - 读远多于写（读写比约 100:1）
   - 缓存命中率目标 > 99%

### 题目 2：设计一个聊天系统（微信/QQ）

```
用户 A 发消息 → 服务器 → 用户 B 收到消息
```

**关键设计决策：**

1. **通信协议**
   - HTTP 轮询（简单但慢）
   - WebSocket（双向实时）— 你的 Flutter 热重载就是用 WebSocket
   - 长连接（TCP）— 微信的方案

2. **消息存储**
   - 写入：消息先写数据库，再推送
   - 读取：用户上线时拉取离线消息
   - 消息 ID：雪花算法（Snowflake）生成全局唯一 ID

3. **在线状态**
   - 心跳机制（每 30 秒 ping 一次）
   - Redis Set 存储在线用户列表

### 题目 3：设计一个新闻 Feed（朋友圈/微博）

```
用户发布内容 → 关注者看到内容
```

**关键设计决策——读模型 vs 写模型：**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 读模型（Pull） | 用户查看时聚合 | 数据一致 | 查询慢 |
| 写模型（Push） | 发布时推给关注者 | 读取快 | 写入慢，粉丝多时扇出大 |
| 混合 | 大 V 用 Pull，普通用户用 Push | 平衡 | 复杂 |

## 系统设计面试模板

面对任何系统设计题，按这个框架回答：

```
1. 需求澄清（5 分钟）
   - 功能需求（做什么）
   - 非功能需求（多少用户、多少 QPS、延迟要求）
   - 估算（存储量、带宽）

2. 高层设计（10 分钟）
   - 画出主要组件（客户端 → API → 服务 → 数据库）
   - 说明数据流

3. 深入设计（20 分钟）
   - 选一个核心功能深入讨论
   - 讨论权衡（为什么选 A 不选 B）
   - 数据库 schema
   - API 设计

4. 扩展讨论（10 分钟）
   - 如何扩展到更多用户
   - 单点故障
   - 监控和告警
```
